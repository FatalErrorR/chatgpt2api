# Go 版验收标准与测试方案

适用范围：`go-v2` 分支的后端移植。前端保持 `main` 上的 Next.js 界面不变，只做适配。

## 已确认的决定（2026-11-20）

| 项目 | 决定 |
| --- | --- |
| 移植范围 | 全部功能：生图链路、号池、代理池、总览统计、图片管理、日志、设置，<br>以及文本接口（chat/completions、responses、messages）、账号导入来源（CPA、sub2api、OAuth、协议登录）、<br>画布和文件任务（image-tasks、editable-file-tasks、ppt/psd）、备份、WebDAV、第三方应用 |
| 数据库 | PostgreSQL（`DATABASE_URL=postgres://…`）。单元测试可用 SQLite 内存库 |
| 真实上游测试 | 在生产服务器上另起 Go 测试实例（独立端口、独立数据库），借 3~5 个账号，生图总数不超过 30 张 |
| 历史数据 | 迁移账号、代理、API key、图片和标签、每日生图计数，以及近 30 天的调用日志 |
| 接口策略 | Go 后端按 Python 版现有的 `/api/*`、`/v1/*`、`/images/*` 等接口格式实现，以 Python 版为准 |

## 验收标准

每一条都必须有可重复执行的证据：测试名、脚本输出或截图。全部通过才可以进入并行上线。

### A. 接口契约

- A1. `docs/contract/python-routes.txt` 列出的 94 个路由，Go 版全部实现，方法和路径一致。
  `/docs`、`/redoc`、`/openapi.json` 除外。
- A2. 契约测试：同一份夹具数据、同一个假上游，对 Python 版和 Go 版发同样的请求。
  状态码一致，响应 JSON 的字段名、类型、嵌套结构一致。
  非确定字段（id、时间、耗时）只比类型。
- A3. 错误响应格式一致：`{"detail": …}` 或 `{"error": {…}}` 保持 Python 版的写法，中文提示文本一致。
- A4. 鉴权一致：管理员 key、普通用户 key、无 key 访问每个路由，得到的状态码与 Python 版相同。

### B. 行为对齐（单元测试和集成测试）

- B1. Python 版 56 个测试文件里的每一个行为测试，Go 版都有对应测试。对照表放在
  `docs/contract/test-map.md`，每行写明 Python 测试名、Go 测试名，确实不迁的写明原因。
- B2. 生图重试策略在假上游下逐项通过：
  - 换号生成按秒超时，总时长不超过上限，最多换 4 次
  - 403 冷却 10 分钟，避开同出口的账号，没有其他出口时退回原出口
  - curl 92 / HTTP/2 断流换号最多 2 次；5 分钟内超过 10 次时熔断
  - 上传限流冷却、模型不存在暂避 10 分钟、回文字重试 3 次、token 失效刷新或剔除
  - **每一条路径结束后，所有账号的并发位都归零**
- B3. 代理池：批量添加、厂商命名、一轮检测、停用并迁移、单代理上限、全有或全无的分配，结果与 Python 版测试一致。
- B4. 统计：今日、昨日、近 7/15/30 天、全部的生图计数，与同一份日志算出的 Python 结果完全相等。
- B5. 图片：分页、标签筛选、分批删除（一次请求只写一次索引）、按自然日清理、按日期预览、缩略图。
- B6. `go test ./...` 全部通过，`go vet ./...` 没有告警，`go test -race ./internal/service/...` 没有数据竞争。

### C. 前端

- C1. `main` 上的 Next.js 前端接 Go 后端，`next build` 通过，`web/test` 的 node 测试全部通过。
- C2. Playwright 用生产形态的模拟数据（100+ 账号且多数不健康、100 个同厂商未命名代理、5,000+ 张图片），
  逐页走查：总览、代理、生图、画布、图片、日志、设置、调试、登录。
  控制台没有报错，没有空白区块，深色模式也要看一遍。
- C3. 关键流程截图对比 Python 版，界面一致：
  批量添加代理、检测并停用、重新分配、按日期删除（含进度条）、定时清理规则、换号生成设置、账号筛选和翻页。

### D. 数据迁移

- D1. 迁移脚本在生产数据的副本上运行：账号、代理、API key、图片索引、标签、每日计数的条数与源文件相等；近 30 天日志的条数与源文件中该时段的条数相等。
- D2. 抽查 20 个账号：token、邮箱、代理、状态、额度、冷却相关字段与源数据一致。
- D3. 脚本可以重复运行，重跑不会产生重复数据。
- D4. 迁移只读源文件，绝不修改。

### E. 真实上游（生产服务器上的测试实例）

测试实例使用独立端口和独立的 PostgreSQL 库，借 3~5 个账号，生图不超过 30 张，不接生产流量。

- E1. 文生图：1:1、16:9、9:16 各 1 张，比例正确。
- E2. 图生图：1 张、3 张、4 张参考图（上游 #426），以及 WebP 参考图（上游 #430）。
- E3. `n=2` 返回 2 张。
- E4. 文本接口：chat/completions、responses、messages 各 1 次，流式和非流式都要测。
- E5. 代理检测：对生产的 100 个代理跑一轮。只检测，不停用。
- E6. 账号刷新、额度查询：结果与 Python 版查询同一账号一致。
- E7. 测试结束后，测试账号的并发位为 0，额度变化与生图张数相符。

### F. 性能与稳定性（假上游，每次请求延迟 30 秒）

- F1. 300 个并发生图请求全部完成，不出现排队上限（Python 版 `api_threadpool_tokens` 默认 256，b807117）。
- F2. 以上压测中，服务自身增加的 p95 开销低于 200 毫秒，管理接口 p95 低于 500 毫秒。
- F3. 连续 2 小时压测，常驻内存稳定，没有持续增长。
- F4. 进程收到 SIGTERM 后，正在进行的请求可以正常结束或明确失败，并发位不泄漏。

### G. 上线

- G1. Go 版和 Python 版并行运行，先切 10% 的流量观察 24 小时：失败率不高于 Python 版同期，没有新的错误类型。
- G2. 回滚演练：一条命令切回 Python 镜像，数据不丢。
- G3. 切换当天，备份 Python 版的全部 `data/` 和 `config.json`。

## 测试方案

| 层次 | 工具 | 对应标准 | 何时运行 |
| --- | --- | --- | --- |
| 单元测试 | `go test`（SQLite 内存库） | B1–B6 | 每次提交 |
| 数据库集成测试 | `go test -tags pg`，用 docker 跑 PostgreSQL 16 | B、D | 每个模块完成后 |
| 契约测试 | `tools/contract`：同一组请求分别打到 Python 和 Go，对比响应结构 | A1–A4 | 每个模块完成后 |
| 假上游 | `tools/fakeupstream`：模拟 ChatGPT 的成功、断流、403、慢出图、上传限流、模型不存在、token 失效等场景 | B2、F | 每个模块完成后 |
| 前端走查 | Playwright，使用生产形态的模拟数据 | C1–C3 | 后端完成后 |
| 迁移演练 | 在生产数据副本上运行迁移脚本，再做对账 | D1–D4 | 切换前两次 |
| 真实上游 | 生产服务器上的测试实例，3~5 个账号，生图不超过 30 张 | E1–E7 | 全部完成后一次 |
| 压测 | 假上游加并发客户端 | F1–F4 | 全部完成后一次 |

### 约定

- 假上游要能同时给 Python 版和 Go 版使用。上游的 base URL 通过配置或环境变量指定，不能写死成 chatgpt.com。
- 测试数据由脚本生成，不提交真实 token。
- 所有测试结果都记录在 `docs/go-migration.md` 的 `进度` 里，写明命令、通过数和提交号。
